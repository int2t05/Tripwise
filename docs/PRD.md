## 1. 产品定义

行程有数是一款多渠道旅行规划桌面工作区。用户可从一句话、网页链接或已保存的攻略开始；Agent 结合网页、地图、天气及可选来源插件，整理一份每日路线草案和出行准备事项。用户能查看资料来源，通过自然语言和结构化操作连续提出修改；每次修订都显示变化，只有用户确认后才成为当前行程。

**产品假设：** 旅行灵感散落在社交平台、网页和地图中；将有用渠道接起来，再把内容转换为有出处的地点、可审阅的时间线和准备清单，能比单次问答更容易做成可执行计划。渠道覆盖是核心产品假设，但“支持渠道数量”本身不是成功指标。该假设尚未经过目标用户试点验证。

**工作名称：** 行程有数 Tripwise。未做商标、域名或应用包名检索。

### 从 Travel Agent 提炼并采用的需求

| 需求模式 | 行程有数的处理 |
|---|---|
| 一句话开始，不强迫先填完表单 | 采用。先识别已知信息，只询问会改变方案的缺项；用户随时可检查和补充简报。 |
| 一次旅行作为上下文容器 | 采用并调整。Trip 保存确认过的日期、地点、预算、偏好、来源和行程；住宿/交通等不同话题可开独立对话，共享已确认的旅行简报。 |
| 先给一份清晰方案，再由用户逐轮修订 | 采用。每次回复最多生成一份完整草案；用户可持续提出修改，查看轮次、差异和当前状态后继续或确认。明确要求比较时，在这一份方案中说明取舍，不并列生成多份。未确认草案不覆盖当前行程。 |
| Agent 过程可见，浏览器不可用时不静默换路 | 采用。显示来自真实 Agent 事件的当前状态、实际工具动作、耗时和结果；逐次展示工具名称及完成/部分/失败状态，本轮调用序列可展开回看。Agent 使用动态工具循环，不映射成固定阶段或百分比；失败后保留实际失败状态与工具结果。详细计划先提交候选地点顺序，再向 Agent 开放路线工具；是否查询及查询哪些路段仍由 Agent 决定。不得伪造进度、回显敏感参数或展示模型内部推理。Agent 可控制同一右侧隔离网页的导航、可见快照和有限滚动，操作时面板保持可见并可停止。来源卡区分搜索摘要、网页正文与图像线索。真实网站、页面注入及目标平台验收仍待完成，见 PR-02 与 AUD-09。 |
| 本地可读的旅行资料 | 调整为桌面端本地优先保存；使用云模型或外部工具前说明会发送哪些必要信息。删除范围需覆盖本地行程及其保存的来源材料。 |
| 代填网页并停在付款前 | 不采用其交易流程。首版不预订、不支付、不自动下单；只提供官方服务入口和提醒。 |
| 行程与地图只作为文档/证据 | 不采用。行程、时间线和地图是本产品的主要审阅界面，必须同步编辑同一份计划状态。 |

Travel Agent 已覆盖多端桌面、旅行上下文、小红书到高德路线示例及可见浏览器；它的公开产品规格以网页交易为中心，并明确不做规划工作区。其他开源项目也已出现多源交叉核验、计划版本和同步地图，因此本产品的差异只能通过“渠道覆盖质量 + 易用的行程审阅和修改 + 出行准备连续体验”验证，不能宣称单项功能首创。详情见调研文档。

## 2. 用户与范围

### 目标用户

个人自由行用户，常从社媒、网页、地图和朋友分享中收集目的地信息，需要把灵感变为可审阅、可检查、可继续修改的行程。首发聚焦中文用户和中国境内 1–7 天城市旅行。

### 首版包含

- 桌面端支持 macOS、Windows、Linux；需要网络；不要求离线运行。
- 主工作区采用左侧旅行栏、中央对话、右侧网页/来源面板；这是用户确认的 UI 方向。更细的行程审阅交互见 [UI/UX 方案](design/UIUX.md)。
- 界面文案从简，用分组、顺序、留白和图标表达层级；不重复说明布局已经表达的信息。来源、隐私、估算和冲突等影响决策的内容在对应对象旁说明。
- 一次旅行作为独立工作区；对话、攻略收件箱、结构化行程、地图、来源和出行准备围绕同一旅行组织。
- 内置通用网页搜索/读取、地点与路线/公共交通估时、天气查询。
- 支持用户粘贴链接或文字作为基础来源入口；其他旅行渠道经连接器接入。小红书连接器采用分阶段策略，见第 5 节。
- 每轮只生成一份完整、可审阅的结构化行程草案，首屏用短摘要和按日时间线呈现。用户可从日期、地点、餐休时段或交通段发起细项修改；意见先预填到对话供用户检查，发送后由 Agent 重排并返回完整修订稿与差异。不并列生成多套候选；用户明确要求比较时，在本份草案中说明取舍。
- 对明确限定为“单日、单餐次、目标片区”的修改，仅当目标片区和仍适用的全部要求均已满足时，才说明行程未变。若用户要求具名店铺且启用了来源核验，默认需有直接提及店名并绑定到该餐次的来源；用户明确接受无来源时把现有候选保留为待选/待核验，则不因该来源缺口重复改写行程，也不得把候选标成已核实。美食街、美食城、商场餐饮区、机场简餐和“自理/自行解决”只算片区或用餐方式，不算已选店面；缺少具体商户时保留待选或待核验状态。
- 输出每日行程、交通与耗时、来源和待核验项、天气穿搭、随身/托运行李清单、预约提醒、就近餐饮和天气/低体力备选。
- 支持多轮局部修改、版本恢复、Markdown 导出及单趟旅行 JSON 备份/恢复；恢复为新旅行，不覆盖现有旅行或共享设置。
- 支持 OpenAI-compatible API 与可选 Codex App Server；默认 API 模式，Codex 模式复用本机登录并使用持久话题会话，不读取或复制 CLI 凭证。模型页默认只显示来源和连接状态；已保存 Key、服务地址和模型名按需展开。信息源与低频高级项分组折叠。

### 首版不包含

机酒车票代订、支付、自动发布/评论/点赞等社媒写入、多人实时协作、完整订单/预订管理、行中导航、离线规划和插件公共市场。

## 3. 核心用户流程

1. **开始：** 用户输入一句话、旅行链接或攻略文字。系统保留草稿，不因打开新旅行而丢失已有未发送输入。
2. **补充与确认：** Agent 提取出发地、目的地、日期、抵离时间、人数、预算、具体住宿地点、住宿区域与偏好、兴趣、节奏、交通、饮食、行李和穿搭条件；对会影响路线的缺项提问。精确酒店名称/地址与区域/房型偏好分开保存，用户确认旅行简报。
3. **查看检索：** Agent 根据当前意图和已有资料，从已启用的网页、地图、天气、浏览器及插件工具中选择需要的步骤。每次工具返回后，模型看到结果、来源和 `error`/`warning`/`info` 反馈，再决定继续查询、修订计划或结束。界面展示实际工具调用、结果和耗时；不展示模型内部推理。
4. **审阅草案：** 每轮只提交一份结构化行程，按日展示地点、时段、交通和来源状态；计划是可继续修改的候选，用户确认前不覆盖已保存版本。
5. **连续修订：** 用户可在对话中提出意见，或直接编辑行程。Agent 以当前话题最近一份未拒绝草案为基线，返回一份完整的新草案，并显示新增、移除、移动、时段和交通变化。最新草案提供「继续修改」入口并聚焦输入框；旧草案保留在对话中。用户可继续修改、拒绝或确认；确认前不改变当前已保存行程。每次确认保存为新版本，历史版本可恢复。
6. **准备出行：** 从已选计划生成逐日穿搭、预约清单、行李、美食和替代方案。内容保留来源或估算标记。
7. **保存与继续：** 用户可在同一 Trip 中另开、切换和删除话题；话题历史互相隔离，旅行信息、来源、已保存行程和准备清单共享。删除话题需确认；删除最后一个话题时自动留下空白「总体规划」。用户可导出 Markdown 或删除整趟旅行。

## 4. 产品需求与验收

| ID | 需求 | 验收标准 |
|---|---|---|
| PR-01 | 对话式旅行简报 | 给一句话后能看到已提取字段，并只被追问会改变方案的缺项；字段可以编辑、留空或标记未知。具体酒店/地址与住宿区域、房型偏好分开填写；只有明确住宿地点可作为路线锚点，抵达/离开时间、住宿区域和固定预约也作为日程约束。同一趟旅行可新建、切换和删除多个话题；删除时只清除此话题与消息，旅行简报、来源、已保存行程和准备清单保留。删除最后一个话题时自动建立空白「总体规划」。 |
| PR-02 | 多渠道工具与可视运行 | Agent 根据意图自主选择已启用的搜索、网页阅读、地图、天气、可见浏览器或 MCP 工具；不执行固定预检或固定质量补查。工具结果统一回传状态、结构化反馈和来源。渠道失败以 warning 返回，由模型选择其他工具或继续；熔断只限制对失效服务或主机的重复请求，不在后台自动切换工具。网页摘要只作线索；动态事实无直接来源时保持待核验。浏览器控制只读、同一隔离页面可见，不操作系统光标，不绕过登录、验证码或访问限制。用户可停止、重试失败来源或继续规划。 |
| PR-03 | 来源与事实状态 | 保存来源链接、类型、状态和获取时间；官方/服务信息、社区经验、用户资料与插件来源分开展示。来源不能支持其未包含的内容。动态开放、预约、价格、天气和交通信息需要直接来源；缺证据时保留待核验，不伪造具体数值。来源冲突或过期时显示现状，交由用户和 Agent 决定后续核验。 |
| PR-04 | 官方事实与游客经验区分 | 官方/服务信息和游客经验分开呈现。系统区分服务数据、政府域名、社区平台、用户导入和未分类来源；域名标签不代替内容核验，社区平台不等于已确认游客身份。UGC 保留链接、作者或发布时间（来源提供时）；存在冲突时并列展示，不让模型静默择一。 |
| PR-05 | 单份草案与连续修订 | 每次模型回复最多提交一份覆盖已确认日期、抵离锚点和明确指定地点的完整草案。首屏先呈现不超过 120 字符的一句话摘要；修订候选的差异紧跟摘要展示，再呈现按日折叠的计划。日期、标题、地点数和餐饮项数用于快速扫读，地点来源、核验细节和安排取舍按需展开。较长的模型补充正文默认收起，计划卡仍是主要产物。当前最新草案默认展开首日，较早草案默认折叠但仍可展开查看。用户提出反馈后，Agent 必须收到最近一份未拒绝草案的结构化内容作为基线，保留未要求改动的安排并提交一份完整修订稿。用户只指定修改某一天时，其他日期的安排保持原样；明确要求全程重规划时可调整全部日期。界面按轮次标记草案，展示新增、移除、移动、时间及路线变化，并明确等待审阅、已有更新、已跳过或已保存状态。用户可从日期、单地点、餐休时间块或相邻交通段发起局部修改；按日菜单分别支持改日期、主题、节奏、增点和排序；单地点菜单分别支持改时段、游玩时长、接驳、名称、片区、说明、替换/移除、前后插入、同日排序和跨日移动；餐休块分别支持改开始/结束时间、时长、类型、标题、片区和说明，也可在前后插入或移除时段；用餐块可指定具体餐馆并转为地点，不重复保留同餐次时间块。餐馆地点可单独替换，地点的预约与门票、条件备选及已有接驳段可就近发起修改；预约事实无直接来源时保持待核验。每个入口只指定对应字段并保留同块其他字段。入口预填日期、目标对象和修改范围并聚焦聊天输入框，不自动发送。日程列表中的地点可拖动调整同日顺序；松手后只预填包含目标日期、两个地点和前后关系的修改意见，不直接改动草案。草案地图画布拖动不在本版范围内。用户发送后，Agent 重新安排受影响时段及相邻交通并返回新草案。固定地点或跨越固定安排的拖动无效，用户仍可通过菜单输入顺序要求。最新未拒绝草案也提供「继续修改」入口；用户可直接在对话中提出意见。明确要求比较时只在单份草案中说明取舍，不生成并列方案。只有确认后才更新当前行程，并保存为新版本；旧版可恢复。用户请求费用时，对本轮草案提供分项费用范围、数量和依据；应用只在币种和全程/人均口径明确时比较预算，未知项目不能视为零或预算内。 |
| PR-06 | 结构化可行日程 | 每日按片区呈现地点、时段、餐休和交通；路线估时绑定来源与方向端点。未知项标为待核验。结构有效但内容有冲突时返回 warning，模型决定补查、调整或交付；系统不自动执行业务重排。明确用户编辑可做确定性归一化，并在回执说明。 |
| PR-07 | 修改预览与版本安全 | 用户可按日期、地点、餐休块或交通段提出修改。模型接收最新未拒绝草案作为基线，提交一份完整修订计划；未指定内容默认保留。结构错误以 error 阻止保存；内容和业务差异以 warning 展示，由模型和用户决定。界面显示差异，只有用户确认后才保存新版本。 |
| PR-08 | 行程/时间线/地图一致 | 三种视图读取和修改同一份已确认行程。切换日期后地图聚焦当日地点，顺序调整后同步更新；未定位地点仍留在列表并可处理。用户可从已确认行程主动生成高德专属旅行地图；发送前预览将离开本机的字段并再次确认，模型不得自动触发。仅在高德书面许可覆盖此场景、数据流和留存方式且官方接口完成验证后开放；未开放时继续提供本机地图和高德官方地点链接。 |

| PR-10 | 替代活动与就近美食 | 用户要求逐日天气时，每个日期都显示与该日期匹配的结构化天气来源或明确未知状态；用户要求每天提供室内雨天替代时，每个游览日需有独立条件项，填写地点、片区、降雨触发和室内类型，不能混入正式时间线。可用时绑定直接地点来源；无可靠来源时保留具体建议并标为待核验，不因此丢弃整份草案。上述明确要求在同一话题的后续修订中持续生效，用户明确撤回后停止强制。预约约满时，备选以结构化条件项关联原停靠点，单独绑定直接支持地点的来源，不占正式行程时段；无来源时可标待核验。详细规划请求中说明延误、人流或降雨时具体压缩什么、保留什么和可替换地点。餐饮匹配忌口/口味和当天区域，显示距离及来源/地图入口。无足够信息时不臆测适配情况。 |

### 4.0 计划交付契约

每轮只产出一份结构化行程。数据字段、日期和类型由 schema 固定；地点、细节、行程风格和表达由用户目标、工具信息及模型判断决定，不用内容评分门槛限制首稿。

- **硬错误：** 仅用于 JSON、字段类型、必填项、日期格式、枚举和工具支持范围等结构问题；回传 `error`，结构无效的候选不保存。
- **建议反馈：** 用户约束差异、路线/时段冲突、信息缺口、来源问题及工具降级回传 `warning`；`info` 表示已执行或按要求跳过。Agent 自主选择补查、修订或交付，warning 不阻止候选审阅。
- **统一回执：** 每次工具结果包含状态、结果摘要、分级反馈和来源。执行端先保存可恢复的工具结果，再交给模型；模型根据回执选择下一步。检索轮次不由五轮之类的质量阶段提前截断；只保留防无限循环的全局工具、调用和超时上限。
- **计划与修订：** 最新一份未拒绝草案是修改基线；模型提交完整修订计划，未要求调整的日期和内容保持不变。界面展示真实工具步骤、反馈和修订差异，不展示思维链。确认后才写入新版本。
- **事实表达：** 来源只支持其实际内容。动态事实、路线数值和价格无依据时标为待核验；工具警告可以触发后续检索，也可以由模型带缺口交付。

### 4.1 实现与验收状态

第 4 节定义产品验收行为；代码覆盖、真实服务结果和未关闭事项统一见[项目进度](PROJECT-STATUS.md)。自动化测试通过不代表真实旅行质量、供应商许可或目标用户价值已经通过。

## 5. 工具和渠道策略

### 内置工具与插件边界

当前已实现渠道和后续 MCP/API 候选见[旅行渠道与 MCP 扩展清单](integrations/MCP-CATALOG.md)。该目录是评估输入，不代表候选渠道已接入或通过发布审查。

- **内置：** 网页搜索/可访问页面读取、地点搜索/地理编码、路线和公共交通估时、逐日天气。结果必须携带提供方、请求时间、地点匹配状态和来源链接。
- **插件：** 社交平台、视频社区、点评、铁路/航班/酒店等来源按用户价值逐步接入。连接器统一返回来源、获取时间、内容类型、地点候选和失败状态；用户不需要手动配置 MCP、Cookie 或命令行来完成普通旅行任务。
- **可选 MCP 接入：** 进阶用户可指定本机 stdio 程序，或远程 Streamable HTTP/SSE 服务；stdio 与 Streamable HTTP 自动协商 MCP 2026 无状态协议，并兼容旧握手服务，SSE 仅用于旧服务迁移兼容。远程地址仅接受 HTTPS（回环开发地址除外），地址不得内嵌凭证、片段或常见凭证类查询参数（包括 `key`）；静态请求头/查询凭证保存在本机 `tripwise-credentials.json`，请求时才注入，OAuth 暂不支持。高德提供官方远程预设并复用已保存的 Web 服务 Key。用户先临时连接、发现工具，再逐项批准；每次规划最多连接 8 个服务，并向模型提供 24 项获准工具。仅开放明确标记为只读且未标记破坏性的工具；高德个人地图生成、导航、打车和票务动作额外拦截。stdio 程序以当前用户权限运行，命令和参数明文保存在本机设置；凭证文件 POSIX 权限为 0600，但同一账户下其他程序仍可能读取，见 [ADR-0013](design/adr/0013-local-json-credentials.md)。远程请求只发到配置的同一主机。失败的连接或只读工具可从来源卡单独重试；重试会重验服务和工具授权，并只重复该来源查询。通过凭证筛查的有界查询参数会保存在本机旅行数据和用户主动导出的旅行备份中；Agent 工具轮次恢复点仅存于本机，不进入显式旅行备份。重启后可显式重新处理末尾未获回复的原始用户消息，并复用已落盘的工具结果；中断时尚未保存结果的工具仍会重跑。通用接入不代表 Tripwise 审核或背书服务代码、数据来源或平台许可。
- **渠道目标：** 首版先确保通用网页、地图、天气的基础流程可用；小红书作为首个优先评估的 UGC 连接器。B 站、大众点评等根据试点中用户实际提供的来源排序，不以“接入一切”作为首发承诺。

### 小红书接入决策

官方开放平台当前公开权限只列出 basic_info；read_notes 仍为规划中，没有可供本产品依赖的通用笔记搜索/读取接口。OpenCLI 提供复用用户 Chrome 登录态的搜索/笔记读取命令，但依赖 Browser Bridge 和易变化的页面 DOM，近期有登录墙、验证码与筛选布局故障记录；这不是官方 API，也不代表平台授权或长期可用。实现细节、源码证据和局限见[渠道调研第 5.3 节](research/scraping-references.md#53-社媒ugc-与用户授权内容渠道)及 [ADR-0008](design/adr/0008-xiaohongshu-opencli-connector.md)。

| 阶段 | 用户可用能力 | 决策 |
|---|---|---|
| 基础版 | 用户粘贴分享链接/文字；通用网页搜索和可访问页面阅读；原链接始终保留 | 必须具备，任何小红书接入失败都回到这条路径。 |
| 可选试点连接器 | 用户安装 OpenCLI/Browser Bridge，在设置提供本机命令并明确启用；Agent 可搜索最多 5 条公开笔记，并读取当前旅行此前搜索到的单篇笔记。显示来源、社区标签、最近运行状态和失败提示 | 已实现但默认关闭。仅作为试点；依赖真实用户 Chrome 登录态与 DOM 适配器。每次操作串行，间隔至少 3 秒；只调用 `search`/`note`，不读评论/收藏/通知，不自动安装、登录或绕过限制。Beta 前完成平台规则、隐私、安全和目标机验收，否则关闭该能力。 |
| 不作为默认实现 | 应用内独立登录会话直接自动抓取；要求用户复制 Cookie 到本产品；不透明托管爬虫；私有接口逆向实现 | 暂不采用。若未来有授权接口或清楚的安全/合规依据，可重新评估。 |

不得自动登录，不得绕过验证码、访问控制或反爬限制，不做批量归档/媒体下载/社媒写入。连接器失效时显示来源级失败，可重试、粘贴链接或跳过；不得静默转到另一套认证会话。小红书搜索 URL 可能包含 `xsec_token`，会随来源保存在本机旅行数据与用户选择导出的 JSON 备份中；它不是登录凭证，但仍应按个人来源链接保护。该策略是产品方案，不构成法律结论；平台政策与法律审查是正式发布的前置门槛。

## 6. 隐私、来源与可靠性

- 默认将旅行工作区保存在用户设备上；用户使用云模型和外部连接器时，在启用前说明哪些提示、链接或文本会发送给谁。数据留在本地不代表推理过程离线。
- 凭证归对应服务商管理，不写入普通日志；连接器必须说明认证方式、授权范围和撤销办法。用户没有授权时不得读取其浏览器内容或账户数据。
- 来源数据用于地点发现和经验参考；营业时间、票价、天气和交通时刻优先以官方或服务提供方为准。搜索摘要不作为最终证据。
- 公开页面、插件或模型不可用时，保留用户输入、已完成检索和草案；给出重试、改用来源、用户补充或继续规划选项。
- 内容仅保存用户明确采纳或主动收藏的必要文字与链接；不默认批量保存图片、视频、评论或无关个人资料。

## 7. 草案交付与试点评估

### 交付底线

- 每轮生成一份可解析、可保存、覆盖本次旅行日期的结构化计划；用户确认前不覆盖已保存版本。
- 修改基于最近一份草案；用户只指定局部时，其他日期保持不变。
- Schema、日期范围或安全边界错误必须修正后才能提交；动态事实、路线、餐馆、预约和天气缺口以 warning/待核验呈现，不阻止用户继续审阅和多轮补全。
- 工具返回真实状态与来源；未查询、失败或证据不足时不生成看似确定的细节。

### 后续试点评估

**North Star：** 用户最终接受或导出一份计划。评估关注完成率、首稿耗时、关键事实的来源或未知标记、严重冲突提示、单一来源故障后的恢复，以及用户主动修改情况。样本不足时只报告观测值，不把模型自评当作用户满意，也不将这些质量指标作为结构有效草案的交付门槛。
