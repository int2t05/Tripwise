# ADR-0018：逐日天气与室内雨天备选

| 项 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-10-24；2026-11-06 复核 |
| 关联 | [PR-05、PR-09、PR-10](../../PRD.md)、[旅行验收](../../PROJECT-STATUS.md)、[ADR-0003](0003-trip-state-and-revisions.md) |

## 背景

TW-11 指出工具成功返回天气数据后，天气只显示在来源面板中，行程卡没有逐日天气状态；室内馆点虽然已经排入路线，也没有明确作为雨天条件备选。用户的计划需要固定结构来审阅和继续修订，但内容详细程度应由用户需求决定。

## 决策

- 用户提出逐日天气要求后，行程每天保存 `forecast` 或 `unknown` 状态。只有成功/部分成功的结构化天气来源包含精确日期行时才写入预报；工具无数据、日期不匹配或来源被移除时写明未知。天气服务明确返回错误/不可用时，将该状态来源附在每日 unknown 上，便于查看失败原因；不从网页摘要或常识补天气。
- 天气工具判断目标日期是否已过去及 16 天预报上界时，使用地理编码返回的目的地时区计算当前日历日期；缺少或无效时区时退回 UTC。设备时区不应改变目的地的天气可用范围。
- 用户提出每天的室内雨天替代要求后，每个有游览安排的日期至少有一个独立条件项，包含地点名、片区、降雨触发和 `environment: indoor`。条件地点不能同时出现在当天正式时间线中；有直接提及地点的有效来源时绑定来源，没有可靠来源时标为 `pending`，不因软性证据缺口拒绝整份计划。
- 逐日天气和逐日室内雨天备选意图按当前话题中的用户消息顺序延续。用户明确撤回后关闭对应约束；之后再次明确提出可以重新开启。用户指定只修改部分日期时，未修改日期仍以最新草案为基线。
- 天气状态进入行程版本、备份、Markdown、修订差异和来源移除处理。天气来源移除后，受影响的逐日状态降为 `unknown` 并清除失效来源 ID。
- 雨天备选的地点结构在候选提交时校验。模型没有抄写来源 ID 时，执行端可在当前可引用来源中按候选地点名自动匹配直接来源；只接受直接包含地点名的成功来源，不要求模型手工复制随机 ID。无直接匹配来源时仍可交付结构完整的待核验条件项。
- 本地校验不独立测量“就近”距离或验证场所实际室内属性。界面提供来源供用户审阅，模型给出的环境分类仍可能有误；来源不足时须明确待核验，不声称已核实。

## 考虑过的方案

| 方案 | 决定 |
|---|---|
| 仅在来源面板展示天气 | 不采用；用户无法按日期把天气与行程安排对应起来，也看不到逐日未知状态。 |
| 要求模型在自由文本中重复天气摘要 | 不采用；无法稳定展示 unknown，也不便维护来源引用和版本差异。 |
| 将雨天替代地点直接排入时间线 | 不采用；条件地点会被误读为实际执行安排。 |
| 为所有行程强制生成天气和室内备选 | 不采用；增加无请求内容。只在用户提出要求时启用相应字段和校验。 |

## 验证与限制

- 自动化测试覆盖日期匹配、目的地时区跨 UTC 日界、16 天预报上界、无数据降级、来源移除、备份兼容、Markdown 和 UI 状态、雨天备选结构校验，以及用户多轮修改中要求保留和明确撤回。
- 真实模型 TW-11 最新运行通过 3 项明确约束，证据见[最终运行](../../evaluation/runs/2026-10-24-tw11-weather-r5/TW-11.json)：天气查询不可用时逐日标记 unknown 并保留失败来源；两日各有独立室内雨天备选且绑定直接地点来源；没有编造降雨概率。人工复核仍不能确认地点距离及场所实际室内属性，这些限制继续显示给用户。
- 结构检查不等于地理距离或场馆属性已被独立核实。缺少直接来源时该项显示为待核验；地点是否足够近、是否确属室内仍需用户结合来源复核。
