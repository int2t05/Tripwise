# ADR-0005：旅行简报提案必须经用户确认

| 项 | 内容 |
|---|---|
| 状态 | Accepted；已实现字段级提取提案、显式确认与并发冲突拒绝。 |
| 日期 | 2026-10-17 |
| 关联 | [PRD](../../PRD.md)、[UI/UX](../UIUX.md)、[TECH](../TECH.md)、PR-01、PR-07 |

## 背景

用户会在自然语言对话中逐步补充目的地、日期、预算和限制。只把这些信息留在聊天记录中会让后续规划难以稳定引用；让模型直接写入旅行简报，则可能把推断误当成用户确认，也可能覆盖用户稍后手动修订的内容。

## 决策

1. 增加 `propose_trip_brief` 工具，只接收本轮明确提到或修正的字段；未提到的字段不进入提案。日期和时间继续由现有简报校验器检查。
2. 提案与助手消息一同保存在 Trip 中，包含生成时的字段基准值和建议值。聊天卡显示每项旧值与新值，并明确说明尚未写入。
3. 用户点击「确认并应用」后，主进程逐项比较提案基准和当前值。目标字段仍未变化或已等于建议值时才应用；有其他值时整份提案原子拒绝，提示打开旅行信息核对。
4. 应用时间随提案保存，重复点击幂等，不重复修改旅行资料。
5. 提案是 `ChatMessage` 上可选的附加字段，因此读取旧 schema v4 消息无需迁移；不改变旅行资料的数据库主结构。

## 理由与代价

- 字段级提案让用户知道模型准备修改什么，并把“模型提取”与“用户确认”分开。
- 基准值检查避免旧回复覆盖后续表单输入；拒绝整份提案保持一次确认的结果一致。
- 用户仍需主动审核；对话里模糊表达、相对日期或矛盾内容需要模型继续追问，不能靠字段提案解决歧义。
- 完整的简报完成度、必填缺项状态和结构化提取评测尚未完成，因此此决策只关闭显式提案确认路径，不宣称 PR-01 全部验收。

## 验证

- 单元测试验证提案只包含与当前简报不同的明确字段，并沿用日期/抵离时间校验。
- 持久化测试验证字段未变时可确认、已被手动修改时拒绝覆盖、重复应用不会再次变更。
- `npm run check` 验证类型、测试与构建；macOS 打包烟测验证聊天主界面可以启动。真实模型生成的字段提取质量仍需固定案例评测。
