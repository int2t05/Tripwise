# ADR-0017：长模型请求的传输时限

| 项 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 日期 | 2026-10-21；2026-10-22、2026-10-24、2026-09-21、2026-11-06 复核 |
| 范围 | 主进程 OpenAI-compatible Chat Completions |

## 背景

GLM-5.3-Flash 的产品单轮时限为 30 分钟。Node `fetch` 底层 Undici 的响应头和分块等待默认值为 300 秒，曾导致请求在产品时限前被中止。来源连接器使用 Electron `net.fetch`，不受此决策影响。

## 决策

- 模型请求使用独立 Undici Agent；响应头、响应体等待上限均为 30 分钟。每次请求仍受模型配置的总时限和用户取消控制。
- GLM 流式空闲上限为 30 分钟。关闭应用时取消请求并释放 Agent；不修改进程全局 dispatcher。
- 响应头超时不自动重发，避免已到达服务商的长请求被重复提交。其他可恢复连接错误最多重试一次。
- 每分钟只记录脱敏阶段、耗时、分块数和字节数，不记录请求/答复正文。
- 资料充分后的普通行程候选切换为 low 推理和 24,576 token 标准输出上限；有可读网页正文的详细首稿使用扩展预算。无可读网页正文的新 GLM 首稿直接使用紧凑 schema 和标准预算，仍保留日期、用户点名地点、餐次、抵离锚点、住宿接驳、休息块及条件备选；应用补入待核验事实。只开放冲突日期的路线修订也从首次请求使用紧凑 schema 与标准预算；主进程按当前草案恢复遗漏的备注及非路线事实，再重新查询路线。有可读网页正文的详细首稿和其他基于旧草案的修改保留完整证据 schema，但 `fact_claims` 可省略；模型只提交正文直接支持的动态事实，执行端为缺少证据的地点补入 `pending`。输出长度超限时仅重试一次，使用紧凑 schema 与标准上限，不再扩大到 65,536 token。结构与硬约束仍由工具校验，内容缺口交由后续对话补充。

## 验证与限制

- 2026-10-22 北京 #26 发现实现回退到 5 分钟，并在超时后重复提交；已修正时限和重试策略。
- 北京 #27 的 9/271 个模型请求完成且无重试，最长约 157 秒；完整规划仍因路线服务未配置而未通过。该运行证明规划链路可完成，不足以证明单次请求超过 5 分钟时仍稳定。详见[北京评测历史运行](../../evaluation/TRAVEL-CASES.md#历史北京运行)。
- 2026-10-24 TW-27 一次运行耗时 566 秒、无草案，模型三次未满足预算/省时比较内容门槛；调整后 r18 用时 159 秒，交付 1 份三日草案，比较缺口标为待补。前后是不同真实样本，不能单独归因于预算调整；结果支持“内容缺项不阻断结构合格草案”，不证明服务延迟已稳定。[证据](../../evaluation/runs/2026-10-24-targeted-r17/TW-27.json) 与 [调整后证据](../../evaluation/runs/2026-10-24-targeted-r18/TW-27.json)。
- 当前 30 分钟空闲上限可能延迟故障恢复；可用真实长请求数据后再调整。模型服务商仍可能主动断开。
- 2026-10-24 最新全量检查结果见[项目状态](../../PROJECT-STATUS.md)；长度重试上限和请求档位由单测覆盖。
- 2026-09-21 北京受限渠道首稿实跑耗时 854 秒；第一份结构化计划在 580 秒生成，模型 32,768 token 输出触发长度重试，其中单次请求最长 505 秒。紧凑重试约 54 秒完成并保留七日与 41 个停靠点，但整轮仍因餐次修补和准备清单耗时 854 秒。随后将无网页正文的新首稿改为从第一次请求起使用紧凑 schema；首轮实跑证据见下一条，完整修订证据见[北京评测](../../evaluation/TRAVEL-CASES.md#北京紧凑首稿与两轮真实修订复验2026-09-21)。来源和限制见[北京评测](../../evaluation/TRAVEL-CASES.md#北京首稿复跑与-glm-长度诊断2026-09-21)。
- 同日紧凑首稿复跑总计 474 秒、首稿 324 秒，24,576 token，无长度/传输重试；必去点和参考点齐全。路线绑定覆盖 3 天，低于前次的 6 天，仍有一处餐馆名和两项时段缺口；两次调用因计划字段/排程校验退回，另有 103 秒研究请求未提交计划。随机模型轨迹不同，这组数据仅证明紧凑 schema 实际生效并可提交，不足以单独证明提速或质量改善。见[北京复验](../../evaluation/TRAVEL-CASES.md#北京紧凑首稿实跑复验2026-09-21)。
- 2026-11-06 北京复跑中，首稿的 `forced_itinerary` 阶段用 1 次请求、52 秒完成，未触发长度重试；上一轮同阶段为 2 次请求、348 秒并触发一次长度重试。该次自动修复仍有一份路线候选被校验延后；9/23 用户修改后的路线修复则以 1 次、28 秒保存成功。来源、模型输出和工具轨迹不同，不能将耗时差值作为受控因果结论。紧凑 schema 与备注/待核验事实保全由定向回归验证，详见[最新北京复跑](../../evaluation/TRAVEL-CASES.md#2026-11-06-北京复跑紧凑路线修订与两轮局部修改)。
- 随后同日复跑将单份路线候选的校验纠错上限从一次增至两次，仍限制最多两轮路线修订。自动修订候选两份均成功保存；第二份首次因时段重叠被拒，反馈纠错后保存，未再延后。此次首稿 18 次模型请求累计 938 秒、最长 414 秒；`forced_itinerary` 3 次累计 510 秒并触发一次长度重试。9/23 局部修改用时 138 秒，9/24 无变化请求完成。运行轨迹、搜索结果和模型输出均不同，不能据此宣称提速或内容达标；详见[最新北京复跑](../../evaluation/TRAVEL-CASES.md#2026-11-06-北京复跑路线重试修复与两轮局部修改)。
