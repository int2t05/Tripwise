# ADR-0003：Trip 状态、行程版本与本地持久化

| 项 | 内容 |
|---|---|
| 状态 | Accepted；当前采用本地 JSON schema v15，保存旅行话题、用户确认的结构化行程、独立日程时段、准备清单、内置连接器开关和非敏感 MCP 配置。 |
| 日期 | 2026-10-18 |
| 关联 | [TECH](../TECH.md)、[UI/UX](../UIUX.md)、PR-01、PR-06–PR-09、PR-12 |

## 背景

旅行简报、话题对话、来源和已确认行程必须保存在同一 Trip 上。Agent 生成的是候选方案；用户明确选择后才成为已确认版本。首版是个人桌面应用，没有云端协作需求。

## 决策

1. `Trip` 保存旅行简报、话题列表、消息、来源、版本和活动版本 ID。消息历史及模型上下文按话题隔离，简报、来源、行程和准备事项由同一旅行共享；当前没有多设备同步。
2. 新生成的助手消息最多包含一份结构化 `ItineraryOption` 草案；用户后续反馈作为新对话轮次，以最近一份未拒绝草案为基线。`buildTripContextMessage` 将该草案作为限长 `latestDraft` 提供给模型，避免只把修改要求留在文本历史中。旧消息中已保存的多候选数组仍兼容读取，不再由新 schema 或 Agent 生成。用户选择后才通过 `saveRevision` 建立不可变快照；恢复历史版本只切换活动版本，不修改旧快照。路线段只能由用户主动采纳后写入，`TransitEstimate` 保存来源、交通方式、查询日期/时刻、方案指标和目标下一站 ID；校验要求路线来源属于当前 Trip 且目标仍是该 stop 的下一站。编辑导致地点端点、顺序或公交查询日期/时刻变化时，自动清除旧估算，避免把旧路线标在新路段上。住宿到当天首站/末站回住宿单独存于可选 `lodgingCommutes`，不混入景点间 `TransitEstimate` 或开放事实；每条接驳绑定明确酒店、边界 stop、方向、成功路线来源及同一方案的数值。主进程校验来源端点顺序、模式、查询日期/时刻和方案耗时/距离；手动编辑改变酒店、日期或边界地点时移除旧接驳。该字段在 schema 中可选；当前旅行备份 v11 保存该字段。
3. 保存结构化草案前，对比当前活动结构化版本的地点增删、跨日移动、相对顺序、时段/停留/说明及方案/每日字段变化；独立日程时段的增删、移动和字段变化也显示在差异中；文本版旧行程无法逐地点比较。草案仍由用户主动保存；消息可选字段 `rejectedItineraryOptionIds` 记录被拒绝的草案，用户可撤销拒绝，主进程禁止保存仍处于拒绝状态的草案。行程页支持编辑结构化字段、地点和日程时段增删及地点同日排序，提交时主进程校验字段，并要求编辑起点仍是活动版本；提交将生成新的不可变快照，继承起点来源引用。未保存的编辑草稿支持最多 50 项语义撤销，同一字段连续输入合并，改回字段起始值会清除已抵消记录；取消丢弃整份草稿，保存生成不可变版本。用户可锁定地点锚点；模型草案生成时即与当前活动结构化方案比对，若固定地点名称、日序、已知日期、时段或固定地点相对顺序变化，则返回修订原因并限次重试，通过后才展示草案。草案保存和手动编辑由主进程再次确保地点、日序、已知日期、时段和锚点相对顺序不变。必须先解除固定并保存新版本，才能改动或删除锚点。历史恢复支持从任意结构化版本选择方案和日字段、匹配地点/时段字段，以及地点和时段的增删、跨日移动、同日排序与整日增删。用户可审阅每项当前值和历史位置，再将选择应用到未保存草稿；整个恢复作为一次语义撤销记录。匹配先按稳定对象 ID，再按两版内各自唯一的规范化地点名或时段类型与标题；重复身份无法对应时显示禁用提示，不按出现序号猜测。恢复缺失日期会先创建空日，地点和时段逐项添加；移动到当前不存在的目标日须同时选择恢复该日。含固定地点的整日不可删除，固定地点不可经移动、删除或字段恢复绕过。新增地点使用新 ID 并清除旧来源、事实、地图定位和路线估算；跨日移动保留当前定位，但清除日期相关事实、路线估算和下一段文字。地点结构变化造成的无效相邻路线及边界住宿接驳会清除，历史住宿接驳不复制。模型每日最多提交 12 个地点，系统最多补齐 5 个航班、机场、住宿或车站硬锚点；最终与手动编辑、历史恢复共用每日 17 个地点上限。每日 1–7 天、独立时段最多 8 项在应用前校验。纯文本版本仍只读比较或整版切换。
4. 旅行数据存于 Electron `userData/tripwise-data.json`，当前 schema 为 v15，启动时校验数据并将 v1–v14 迁移到当前结构。无法证明的旧日期、地点来源和坐标含义保留为待确认或待定位，不自动猜测。写入串行化并通过临时文件替换；损坏或未知版本会报错并保留原文件。
5. 准备事项用 `itineraryDate` 表示适用行程日，用 `dueDate` 表示完成截止日；两者分开存储、分组与展示。旧版单日期仅在餐饮/备选的停靠点快照与行程版本可证明其为适用日时才自动归类，其余保留为 `legacyDate`，要求用户确认或清除，避免把预约截止时间误配到某个行程日。
6. 凭证与旅行资料分开存储；当前存储规则以 [ADR-0013](0013-local-json-credentials.md) 为准。用户可导出单趟 Trip 的 JSON 并恢复为新 Trip，但没有自动数据库备份、云同步或损坏文件原位恢复流程。当前导出 `tripwise-trip-backup` v11，接受 v1–v10 并迁移已知旧字段；备份保存当前旅行 schema，包括多话题、GCJ-02 坐标、可选住宿接驳、逐日天气和条件备选。备份 JSON 不加密且不含凭证，可能包含用户导入的网页正文。用户也可导出 Markdown 和删除 Trip。
7. 默认只保留用户主动采纳/导入的来源链接和摘要；不后台归档社媒媒体或读取系统浏览器登录态。

## 理由与代价

JSON 数据可直接检查、迁移逻辑简单，适合目前少量本地旅行；串行原子替换避免并发写入覆盖。日期分开建模使按行程日准备与截止提醒互不混淆；旧数据不做无法证明的语义猜测，代价是部分用户需要在清单中确认旧日期。随着数据体量和多实体查询增加，可再用可验证的数据迁移切换到 SQLite。

代价是需要自行维护 schema 校验、迁移和损坏恢复；临时文件替换提供原子可见性，但当前没有 fsync 或自动数据库备份，因此不承诺断电级持久化。用户的 JSON 备份按单趟旅行导入为新记录；Markdown 仅用于阅读和分享，不承担恢复职责。

## 验证

- `tests/core.test.ts` 验证候选拒绝/撤销及重启恢复、拒绝状态下无法保存、候选版本保存/重启恢复、固定锚点跨候选保留与冲突拒绝、显式解锁、编辑版本追加与过期/无效输入拒绝、路线证据来源/目标站绑定及地点改序/日期变化后的失效处理、住宿接驳方向/端点/方案数值校验、来源失败后禁止采纳、酒店变化清理与 v8 备份往返、日程时段冲突与版本差异、旅行话题隔离和旧单流迁移、v9 数据和 v3 备份的时段迁移、准备事项日期拆分与旧日期确认、旧版旅行备份迁移、v7 话题与 GCJ-02 备份往返、恢复为新 Trip 且不改共享设置，以及未知 schema 保留原文件。历史恢复自动测试验证只应用所选字段/结构操作、来源与定位清理、地点/时段增删与排序、跨日移动和缺失目标日依赖、固定安排限制、重复身份保护及每日数量上限。
- 版本号校验会拒绝不支持的格式；新字段须通过显式迁移加入，禁止静默重置用户旅行数据。

## 未来复审条件

- 若增加多设备同步、复杂查询或较大来源库，先评估 SQLite/备份格式和恢复 UX。
- 若未来允许纯文本版本进行选择性恢复，或让对象身份跨旅行、协作用户复用，需重新设计匹配身份、冲突处理和来源安全；当前歧义对象需用户在编辑器中手动调整。
