# ADR-0002：内置工具与外部连接器边界

| 项 | 内容 |
|---|---|
| 状态 | 已采纳内置工具契约与扩展边界；用户已选择高德完整地图产品族。高德服务数据留存许可仍是正式发布阻断项。 |
| 日期 | 2026-10-17 |
| 关联 | [TECH](../TECH.md)、PR-02、PR-03、PR-04、PR-11 |

## 背景

用户把渠道多样性和工具开发作为产品核心，希望接入天气、地图、通勤、网页资料和社交攻略等来源。各渠道的 API、登录态、内容结构、授权与维护成本不同；如果全部塞进单一爬虫或要求每个来源都经同一插件协议，会牺牲可靠性并扩大权限。

开源参考给出不同做法：Agent-Reach 关注渠道适配、健康诊断和 fallback；桌面 Agent 客户端提供 MCP 连接器管理；旅行项目通常将自己的地图、天气或路线能力保留为产品内工具。它们证明了模式存在，不证明某个协议能自动解决数据许可、安全或可用性问题。

## 决策

采用“产品内工具契约 + 可替换提供方适配器 + 有边界的外部连接器”：

1. **产品内置基线能力：** 网页搜索、用户主动打开页面后的可见文字导入、地点/地理编码、路线与公共交通估时、天气。它们是产品能力，底层服务商可替换。
2. **来源适配器：** 社交、视频、点评和其他专门来源按用户价值逐项接入；每个适配器申明能力、授权方式、数据范围、健康状态和失败恢复。通用本机 MCP 管理已实现，但尚无小红书内置结构化读取，也不代表已审核任意接入服务。
3. **统一产品契约：** 连接器接收最少必要的查询上下文，返回结构化条目、来源链接、获取时间、可用时的发布时间、地点候选、状态、是否可重试和后续动作。
4. **MCP 可选：** 首版仅支持用户手动配置的本机 stdio MCP 服务；无远程 HTTP transport、公共插件市场或自动发现。通过官方 TypeScript client SDK 连接；内置工具仍由产品自己的契约执行，不要求经过 MCP。
5. **权限界面：** 设置页明确提示本机命令以当前用户权限运行，配置命令/参数明文保存在本机设置；凭证存储方式以 [ADR-0013](0013-local-json-credentials.md) 为准。服务需用户手动启动发现工具，并逐项批准。每轮最多启用 8 个服务和 24 项工具。禁用从下一轮生效，删除需确认并清除凭证。
6. **只读门槛与限制：** MCP 工具必须由服务标记 `readOnlyHint=true` 且未标记 `destructiveHint=true`，用户再明确勾选后才能暴露给模型。MCP 注释是服务自述，不能阻止恶意代码产生副作用；工具只能来自用户信任的服务。Tripwise 不提供预订、支付或社交写入的一方工具。
7. **失败隔离：** 每个来源单独返回状态；网页搜索、天气、Agent 地点查询可持久化不含凭证的白名单查询参数，用户逐条重试或跳过。路线段估算仍通过行程路线控件重查。末尾待回复用户消息可保存不含系统提示词、凭证的有界工具轮次检查点，重启后由用户显式恢复并复用已完成结果；未落盘的调用会重跑，不做后台自动恢复。第三方登录态来源的重试仍需目标系统验证。
8. **当前地图提供方：** 用户已选择高德地图产品族；实现统一使用高德 JS API 底图及高德 Web 服务 POI/路线，不调用 OSM/Nominatim，也不跨地图服务回退。高德坐标以 GCJ-02 保存，既有 WGS84 坐标只保留、不绘制并提供重新定位。高德服务数据本地留存许可尚未确认，详见 [ADR-0010](0010-map-provider-compatibility.md)，不能因此宣称正式发布已获批准。
9. **路线估算交互：** 用户逐段请求高德路线并可将选中估算写入行程版本。路线数据的本地持久化许可仍待确认，是发布门槛；结果不自动绘制道路几何，票价以整数分保存、未知费用保留未知、费用不冒充全程预算等产品语义继续保留。

### 最小结果字段

`provider/tool_id`、`capabilities`、`status`、`retryable/next_action`、结构化 `items`、`canonical_url`、`fetched_at`、可用时的 `published_at/author`、`geo_candidates/confidence` 与 `claims/evidence_refs`。具体接口 schema 在实现前再按工具类型定义，不假装所有来源具有同一能力。

## 后果

### 正面

- 旅行产品能固定保证搜索、地图、天气等基础工作流，同时保留替换数据提供方的空间。
- 新渠道可逐个实现与审查，来源级状态与错误信息能支撑用户继续完成任务。
- MCP 作为互操作选项存在，但不会把网络工具、桌面权限或用户数据开放给所有插件。

### 代价

- 产品需要维护一层工具契约和各提供方映射。
- MCP 服务的认证、兼容性、数据流和供应链风险需要额外审查。
- “渠道覆盖”不再等同于抓取所有可见内容；未通过许可或安全门槛的来源只能使用用户粘贴/公开网页路径。

## 小红书边界

手工粘贴链接或文字是基础能力。结构化只读检索属于独立试点，必须先过 PRD 的平台规则、隐私、安全和维护审查；当前提案不承诺开放平台有通用笔记搜索 API。不能自动登录、绕过验证码/访问控制/反爬，不要求用户复制 Cookie，不提供批量媒体归档或社媒写入。可见网页面板、普通网页读取和登录态连接器是不同能力，分别授权。

## 替代方案

### 只采用 MCP

能复用外部工具生态，但会将产品关键路径依赖于外部服务部署、schema 和权限质量；不适合作为网页/路线/天气基础能力的唯一边界。

### 所有渠道都做内置专用爬虫

可能更可控地打磨体验，但每个站点都增加解析、登录、失效维护和平台风险；不适用于未验证的全渠道承诺。

### 向普通用户开放任意插件安装或默认启用

能快速扩展，但用户难以理解来源、权限和供应链风险；首版不提供市场，也不自动启用。高级用户手动填写本机命令仍会获得当前用户权限，因此界面需先展示警告和逐工具授权。应用不具备 OS 级进程沙箱，这是现有选择的已知限制。

## 人工审计

| 检查项 | 需要的证据 | 关闭标准 |
|---|---|---|
| 用户可理解授权 | 连接器能力、数据流、认证和撤销流程原型 | 用户能看懂该工具读取什么、发送给谁、怎样关闭 |
| 插件隔离 | 真实调用路径、进程边界、凭证访问控制 | MCP 以独立进程运行，只注入该服务配置的环境凭证并按工具传参；本机凭证 JSON 未加密，进程仍与应用同属当前 OS 用户，文件/网络权限隔离尚未实现 |
| 渠道发布门槛 | 每个来源的许可/平台政策、维护和失败方式 | 一方审查通过；未通过渠道仍可手动导入 |
| 失败恢复 | 自动化测试覆盖失败来源参数白名单、重试更新和跳过；打包应用来源卡逐项操作烟测 | 网页/天气/Agent 地点有实现与持久化测试；末尾未获回复消息的模型工具轮次已加入跨重启检查点恢复与去重集成测试；平台登录态来源仍待验证 |
